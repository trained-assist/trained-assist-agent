# User Scenarios

Живая документация пользовательских сценариев. Используется как:
1. **Спецификация поведения** — что должен делать бот, точно и без двусмысленностей
2. **Основа для тестирования** — каждый шаг сценария = тест-кейс
3. **Онбординг** — новый разработчик читает сценарии и понимает систему

## Структура

```
docs/user-scenarios/
  README.md          ← этот файл
  core/              ← общие инварианты всех продуктов и каналов
    01-channel-concurrency.md  ← CH-01–CH-11: Telegram single-run + параллельные Web/чаты
  recruiter/         ← домен: рекрутер с HeadHunter
    01-full-end-to-end.md       ← сквозной flow: от коннекта до отправки оффера
    02-ats-setup-and-scoring.md ← настройка критериев подбора
    03-response-regen.md        ← перегенерация ответа кандидату
    04-cold-search.md           ← холодный поиск (проактивный)
    05-vacancy-switch.md        ← смена активной вакансии
    06-hh-reconnect.md          ← переподключение HH после истечения токена
```

## Цели и скоуп

`GOALS.md` — продуктовые цели и явный out-of-scope список. Это источник истины
для автоматического гейта релевантности (стадия «Фиксер», `src/issue-fixer.js`):
он решает, чинить ли issue автоматически, читая этот файл и сценарии ниже, а не
хардкод в промпте.

Добавление сценария не отменяет ограничения GOALS.md на автоматическое изменение
архитектуры, неоднозначные задачи и Web UI. Наличие документа — не разрешение
автономно менять продуктовую concurrency policy.

## Формат сценария

Для каждого нового или изменяемого сценария обязательны:

- **ID и статус** — стабильный идентификатор; requirement, implemented или verified с evidence.
- **User story** — кто пользователь и какое поведение ему нужно.
- **User value / Зачем** — какой полезный результат получает пользователь или какой ущерб предотвращается. Не «так проще в коде».
- **Контекст** — что уже есть у пользователя (state), права, подключённые токены, нужные ресурсы и изоляция теста.
- **Шаги** — реплики/действия пользователя → ожидаемое поведение системы.
- **Validation** — конкретные проверяемые assertions; для ограничения — также положительный сценарий того, что оно НЕ запрещает.
- **Edge cases** — границы, конкуренция, сбои, restart/retry, неоднозначный ввод.
- **Evidence** — ссылка на test file/test name/PR и проверенную ревизию; что ещё не проверено, указать явно.

Для ограничения обязательно описать его **scope и anti-goals**. Например,
«один активный run в Telegram-диалоге» НЕ означает «одна задача на профиль или
папку». Должны быть тесты как последовательности одного диалога, так и реального
параллелизма разных sessions в одном profile/workDir.

Существующие сценарии дополняются этим форматом при изменении их поведения;
не требуется массовая перепись исторических документов в одном PR.

## Запуск

Сейчас сценарии — только документация. Следующий шаг — runner, который их исполняет.
Планируемый runner: `tests/scenario-runner/` — отправляет шаги через `/run` API, судья-LLM оценивает ответы.

Для concurrency/ownership/idempotency LLM-судья **не является доказательством**:
нужны deterministic integration tests реальных entrypoints с fake engine,
barriers/latches, фактическими start/end и контролируемой capacity. Пять
`accepted` запросов не доказывают пять параллельных executions. CI/evidence
отмечаются отдельно от наличия Markdown.
