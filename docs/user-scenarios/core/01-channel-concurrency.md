# CH-01–CH-11 — понятный Telegram и параллельные Web/чаты

**Домен:** core, все продукты/провайдеры и движки.  
**Требование владельца:** 25.09.2026.  
**Родитель:** [#1365](https://github.com/trained-assist/trained-assist-agent/issues/1365).  
**Нормативный контракт:** [Channel execution concurrency](../../architecture/channel-execution-concurrency.md).

**Статус:** сценарии и acceptance checklist. Новые automated tests и live canary ещё не подтверждены этим документом. Чекбоксы ниже относятся к проверенной реализации, а не к написанию Markdown.

## User story

Как пользователь, я хочу в одном Telegram-диалоге управлять одной исполняющейся задачей, а в других чатах и отдельных Web-сессиях работать параллельно в том же профиле/проекте/папке.

## User value — зачем это нужно

В Telegram один поток ввода/вывода. Параллельные задачи в нём смешивают ответы и управление: непонятно, к чему относятся «Стоп», «Дополнить» и следующий текст. В Web у сессий разные рабочие области; пользователь видит вход, выход и управление каждой. Последовательность всего профиля или папки в этом случае только мешает.

**Что ограничение НЕ запрещает:** несколько сохранённых сессий в чате; очередь следующих задач; несколько одновременно работающих сессий одного профиля, проекта или workDir в разных чатах/Web. Ресурсное ожидание — отдельно от продуктового правила.

## Контекст тестов

Один тестовый профиль P, один проект J и один workDir D. Sessions S1–S5 разные, requestId/executionId уникальны. Fake engine умеет ждать barrier и сообщать фактические start/end. Для positive-parallelism tests capacity явно >= 5, RAM/provider checks контролируются fixture. Иначе «все accepted, но стоят в очереди» можно ошибочно принять за параллелизм.

TG endpoints default/recruiter/freelance, два обычных чата, forum topics A/B, два actor в одной группе; Web открывает несколько сессий. Один Telegram-диалог — чат конкретного бота, а в форуме отдельная тема согласно tg-bot#255. Разные actor одного диалога не создают разные lanes.

Все данные/токены/истории/media/runtime/SQLite/queue roots и KV/DO/R2 bindings — только staging/test. Fake outbound запрещает отправку production пользователям. Before-test guard проверяет realpath/bindings, не только имя профиля. No live run на папках production.

## Шаги и Validation

### CH-01 — две сессии в одном Telegram-диалоге

**User story:** хочу начать следующую задачу, не теряя управление текущей.  
**Value:** ответы и команды не смешиваются.

Запустить A в S1 и удержать engine barrier. В том же диалоге явно выбрать/создать S2 и отправить B. Ожидание: B принята в очередь, но не running; история S2 может существовать. «Дополнить A» остаётся в A. Освободить A, затем B начинает исполнение.

- [ ] `maxActive(telegramConversationLane) === 1`, даже при разных sessionId/projectId/engine.
- [ ] B действительно starts только после terminal/подтверждённой остановки A; input не потерян.
- [ ] Stop/supplement адресуют точный execution, не новую выбранную session по mutable pointer.

### CH-02 — разные Telegram-чаты, один профиль и папка

**User story:** хочу вести независимые задачи одного проекта в разных чатах.  
**Value:** общая папка не превращается в искусственную очередь всего проекта.

Запустить A/S1 в чате X и B/S2 в чате Y, с одинаковыми P/J/D. Оба engine удержать barriers.

- [ ] A и B одновременно running, интервалы перекрываются при достаточной capacity.
- [ ] Нет profileId/projectId/workDir mutex; output и Stop остаются у своего execution.

### CH-03 — пять Web-сессий одного профиля/папки

**User story:** хочу одновременно наблюдать пять независимых задач в отдельных рабочих областях.  
**Value:** каждый вход и результат виден отдельно, незачем ждать соседнюю задачу.

Открыть S1–S5 одного P/J/D и запустить пять работ, удерживая barriers.

- [ ] Все пять одновременно running при capacity >= 5; одного accepted/queued недостаточно.
- [ ] Нет общего web chatId=0 lane или профильной блокировки.
- [ ] Prompts/MCP configs/temp outputs раздельны; Stop S3 не останавливает остальные.

### CH-04 — Web и Telegram работают параллельно

**User story:** хочу продолжать работу в Web, пока бот выполняет другую задачу.  
**Value:** выбор интерфейса не блокирует весь профиль.

A/S1 из Telegram и B/S2 из Web используют одинаковые P/J/D.

- [ ] Оба engine running одновременно; Web Stop/status относится только к B.
- [ ] TG output остаётся в TG, Web output и файлы — в Web.

### CH-05 — одна сессия открыта в двух интерфейсах

**User story:** хочу видеть одну целостную историю, даже открыв её в двух местах.  
**Value:** не возникают конкурирующие версии транскрипта.

Открыть S1 в двух Web-вкладках, затем повторить с TG+Web. Одновременно отправить два разных запроса. Параллельно запустить независимую S2.

- [ ] `maxWriters(S1) === 1`; второй запрос видимо ждёт/сохраняется, не исчезает.
- [ ] S2 работает параллельно; запрет не расширился до профиля.
- [ ] Повтор одного requestId не становится вторым execution; чтение истории не блокируется.

### CH-06 — боты и темы форума

**User story:** хочу независимые диалоги в разных ботах и темах, но один поток внутри каждой темы.  
**Value:** reply/Stop/media не попадают к соседней задаче.

Запустить задачи в двух topics A/B и разных endpoints; в A послать вторую задачу.

- [ ] Один run на `(endpoint, chat, topic)`, topics A/B независимы.
- [ ] Второй run A ждёт; завершение media/GTD/retry возвращается в A.
- [ ] Лички и нефорумные группы сохраняют one-chat rule; legacy topic/key migration не смешивает данные.

### CH-07 — два участника одной группы

**User story:** хочу понимать, от чьего имени работает бот и кто управляет задачей группы.  
**Value:** профиль не меняется вслед за последним отправителем, чужая история не раскрывается.

Группа связана с P. Два разрешённых actor отправляют разные задачи в один lane; затем неизвестный/неразрешённый actor пробует запуск и Stop.

- [ ] Actor и principal сохранены отдельно; для группы используется её авторизованный binding.
- [ ] Разные actor не дают двух активных runs в одном lane.
- [ ] Неподтверждённый binding не выбирает произвольный profile; чужой Stop/history/file access отклонён.

### CH-08 — очередь, Stop, retry, GTD и restart

**User story:** хочу, чтобы принятая задача пережила сбой без потери, дубля и смены адреса.  
**Value:** не приходится повторно объяснять работу или искать ответ в другом чате.

Old-version writer принимает A и queued B; новый runtime восстанавливает состояние. Повторить совместимый rollback. Во время stop_requested A отправить C; отдельно проверить clearChat/wakeup/timeout, пока старый engine ещё жив. GTD/retry пытается повторно продолжить ту же задачу.

- [ ] Stable request/rootTask identity, session/project/attachments/reply/lane и очередь сохранены.
- [ ] Новый владелец не запускается, пока старый реально исполняется; terminal/dedup исключают повтор.
- [ ] Stop queued B предотвращает её start, не меняя A и чужие lanes.
- [ ] New-only Web record не downconvert в chatId=0: compatible bridge либо явный отказ unsafe rollback без потери записи.
- [ ] Lost ACK не дублирует execution; delivery failure не повторяет model/provider mutation.

### CH-09 — Web продолжает Telegram-created session

**User story:** хочу продолжить ту же работу в Web, а при возврате в Telegram понимать изменения.  
**Value:** история общая, но ввод не уходит незаметно в неизвестный контекст и файлы не утекут в другой интерфейс.

TG указатель — S1. Прочитать, затем продолжить S1 из Web и вызвать result/file/image/label tools. Вернуться в Telegram. В отдельном варианте TG уже выбрал S2 до Web-продолжения S1.

- [ ] Web read не меняет pointer, Web run пишет в S1 после access/session-writer checks.
- [ ] Web result tools не вызывают Telegram через CHAT_ID/env; replyToRef Web сохранён.
- [ ] При возвращении до продолжения показана отметка об изменениях в Web, авторизованный журнал и выбор сессии; cursor отражает показанное, не «прочитанное».
- [ ] Web-продолжение S1 не возвращает TG pointer с S2 на S1.
- [ ] Чужой principal не может открыть/продолжить session или скачать её file refs.

### CH-10 — переключение выбора при queued input

**User story:** хочу, чтобы уже принятый текст остался у выбранной мной задачи.  
**Value:** смена пикера не переадресует сообщение молча.

При running A принять B для S2/J1 в очередь. До start B выбрать S3/J2. Затем освободить A. Поздний STT/media результат относится к исходному input.

- [ ] B исполняется с сохранёнными S2/J1/source/reply, не по текущему pointer S3/J2.
- [ ] Неоднозначный input остаётся awaiting-selection и не создаёт execution.
- [ ] Supplement остаётся у A; ни picker, ни поздняя media не обходят TG lane.

### CH-11 — capacity и конфликт одного файла

**User story:** хочу видеть настоящую причину ожидания и продолжать независимую работу.  
**Value:** защита ресурсов не маскируется под запрет параллелизма профиля.

Снизить capacity, принять несколько разных sessions P/J/D, затем освободить slot. Отдельно смоделировать конфликт конкретного output file/operation при другой независимой работе.

- [ ] Ожидание capacity имеет явный статус, после освобождения задача запускается.
- [ ] Нет отказа «одна задача на профиль/папку»; разумные существующие resource limits не меняются молча.
- [ ] Конфликт одного ресурса решён локально; независимая session того же проекта продолжает работать.

## Edge cases для всех сценариев

Legacy audience, explicit unknown endpoint, отсутствующий thread, stale callback, две первые messages без sessionId, смена profile binding во время задачи, engine fallback и reconnect не должны менять адрес уже принятого execution или ослаблять guards. Direct Web retry и gateway retry проходят тот же admission. Async/background providers не выбирают actor/principal/roots из model text.

## Evidence и защита от ложного зелёного

Existing reference: `test/per-chat-queue.test.cjs` и `src/runner-chat-queue.js`. Они покрывают базовый helper, но не доказывают прохождение этой матрицы через HTTP/runner/durable recovery.

Каждый implementation PR указывает `CH-ID → test file/test name → exact SHA/result`. Проверять реальный start/end fake engine через barriers, а не только отсутствие ошибок, disabled button, accepted receipt или субъективную LLM-оценку. Для запрещённого overlap и разрешённого parallelism обязательны обе группы assertions.

Сценарии read/queue/restart используют изолированные данные. Live canary — отдельное evidence после automated tests, на тестовых аккаунтах/ботах. Не менять эти ожидания под текущую реализацию, чтобы сделать CI зелёным.
