# Exhibition — Каталог участников выставки → сайт продаж

**Домен:** Обработка участников выставок (Flexi Consulting)  
**Длина:** ~8 фаз  
**Охват:** от ссылки на выставку до задеплоенного сайта-каталога с классификацией целевых компаний  
**Скиллы:** `exhibition-pipeline` (полный конвейер), `exhibition-company` (одна компания) — **LIVE сегодня**  
**Статус:** базовый конвейер ✅ IMPLEMENTED; **проверка реестров перед классификацией** — 🔵 НОВОЕ ТРЕБОВАНИЕ (не текущее поведение)

> Этот сценарий документирует **живой** конвейер обработки выставок. Отдельно и явно
> помечен **новый запрошенный шаг**: проверка реестра (санкционные списки и/или
> официальный реестр компаний) **до** классификации target/near-target/not-target.
> Новый шаг ещё не реализован — его нельзя считать текущим поведением.

---

## Контекст (начальный state)

- Пользователь дал URL выставки (или название) и просит построить каталог продаж
- Доступны API-ключи: DaData (ИНН по названию), Checko (финансы по ИНН)
- Локальный каталог/сайт-шаблон: `/Users/vova/Code/exhibitions/exhibitions/<slug>/index.html`
- Данные исследований: `/Users/vova/Code/flexi-consulting-exhibitions/<slug>-results.json`
- Определение целевой компании: российский **производитель** под собственной маркой,
  не дистрибьютор, не иностранный бренд, не сервис

---

## Сценарий

### Шаг 1 — Найти каталог участников

```
User: вот выставка https://EXHIBITION.ru — собери каталог участников и сделай сайт
```

**Ожидаем:**
- Бот ищет страницу каталога участников (`/participants`, `/exhibitors`, `/companies`, `/catalog`)
- Проверяет digital-поддомен (`catalog.`, `digital.`, `expo.`) — там есть сайты/почты компаний
- Определяет базу каталога (`CATALOG_BASE`) и способ пагинации

**Validation:**
- Найден источник списка участников; `CATALOG_BASE` зафиксирован
- Если каталог не найден — честное сообщение, а не выдуманный список

**Контракт шага (если бы это был playbook item):** `agent / researcher / bachelor / small` — discovery-шаг.

**Статус:** ✅ IMPLEMENTED (`exhibition-pipeline` Phase 1)

---

### Шаг 2 — Спарсить список участников

**Ожидаем:**
- Скрапить список: имя бренда, стенд/секция, href в digital-каталоге, страну
- Поддержать варианты: Tilda T-Store API, HTML-страницы, JS-массив `EX`
- Нормализовать имена (снять HTML-entities, lowercase, убрать не-алфанум)

**Validation:**
- Получен дедуплицированный список компаний
- Нет мусорных/пустых имён

**Контракт шага:** `programmatic` — детерминированный скрейп, без LLM-суждения.

**Статус:** ✅ IMPLEMENTED (`exhibition-pipeline` Phase 2)

---

### Шаг 3 — Обогатить каждую компанию (ИНН, финансы, сайт)

**Ожидаем:**
- По названию — ИНН через DaData (`suggest/party`)
- По ИНН — юр. лицо, ОКВЭД, регион, статус и финансы через Checko (`api.checko.ru/v2/company`)
- Со страницы каталога — сайт и email
- Параллельно (`ThreadPoolExecutor`, ~8 воркеров), таймауты на запросы

**Validation:**
- У российских компаний проставлен ИНН, где он находится
- Для Checko сохранён **ОГРН** (ссылка `checko.ru/company/{OGRN}`, не по ИНН)
- Недоступность API не валит весь прогон — компания остаётся с `nt`-кандидатом

**Контракт шага:** `programmatic` (внешние API + детерминированный парсинг).

**Статус:** ✅ IMPLEMENTED (`exhibition-pipeline` Phase 3, `exhibition-company` Steps 1–3)

---

### Шаг 3.5 — 🔵 НОВОЕ ТРЕБОВАНИЕ: проверка реестров ПЕРЕД классификацией

> **Это новое требование, а не текущее поведение.** Сегодня конвейер переходит от
> обогащения сразу к классификации target/near/not-target (Шаг 4). Запрошено вставить
> **реестровую проверку до классификации**, чтобы не предлагать клиентам компании под
> санкциями или несуществующие/недействующие юрлица.

**Ожидаем:**
- Для каждой компании с найденным ИНН/ОГРН выполняется проверка:
  - **санкционные списки** (например, консолидированный список США/EU/UK или РФ-перечни) —
    по ИНН/ОГРН/названию;
  - **официальный реестр** (ЕГРЮЛ/ФНС) — статус: действующая / в процессе ликвидации /
    ликвидирована / исключена / банкротство.
- Результат — флаг `registry_status` (`ok` / `sanctioned` / `not_found` / `inactive`)
  и источник проверки; он попадает в запись компании и в карточку сайта.
- Если компания `sanctioned` — она **не может** получить `t:1` (target), максимум —
  явная пометка `sanctioned`/исключение из целевых.
- Если `not_found`/`inactive` — максимум `nt:1` и предупреждение (как с отсутствием ИНН).

**Validation:**
- Ни одна компания из санкционного списка не попадает в `t:1`
- Недействующее юрлицо не попадает в `t:1`
- Пометка реестра видна на карточке (badge/текст) и в `results.json`
- Проверка вызывается **до** `classify_type` / `classify_revenue`

**Контракт шага (предлагаемый playbook item):** `programmatic` — вызовы реестров
детерминированы; при неоднозначных совпадениях — `agent / researcher / bachelor / small`
для ручного разбора пограничного совпадения.

**Статус:** 🔵 PLANNED (новое требование, не реализовано)

---

### Шаг 4 — Классифицировать: target / near-target / not-target

**Ожидаем:**
- **Шаг 4a — тип:** страна, ОКВЭД (13.x/14.x — производитель; 46.x/52.x/73.x — торговля/сервис),
  слова-маркеры в названии («Дистрибьютор», «Импорт», «Торговый дом», «ТД»)
- **Шаг 4b — выручка:** пороги (в млн руб): unknown → `nt:1`; < 150 → `nt:1`;
  150–1000 → `t:1`; 1000–5000 с прибылью ≤ 100 → `t:1` (Skolkovo-кандидат); > 5000 → `nt:1`
- Жёсткие правила: **NO INN = NO t:1**; `near_candidate` (неясный тип) → максимум `nt:1`;
  неизвестная выручка → `nt:1`, **не** исключение; Belarus ≠ target

**Validation:**
- `t:1` только при подтверждённом ИНН + выручке в диапазоне + типе «производитель»
- Реестровый флаг из Шага 3.5 учитывается (`sanctioned`/`inactive` не могут быть `t:1`)
- Каждый класс имеет обоснование

**Контракт шага:** `programmatic` (детерминированный классификатор, `risk-engine`-стиль),
пограничные случаи — `agent / researcher / master / medium`.

**Статус:** ✅ IMPLEMENTED (без учёта реестрового флага — он появится вместе с Шагом 3.5)

---

### Шаг 5 — Собрать `EX`-массив

**Ожидаем:**
- Для каждой компании — запись `{id, n, t, nt, inn, ogrn, w, e, href, ru, rev, prof, ry}`
- `b` (описание) пишется вручную для целевых
- `ogrn` обязателен для Checko-ссылки
- 🔵 Новое: поле реестрового статуса (`registry_status`, источник)

**Validation:**
- Каждый `t:1` имеет непустое `b`
- `ogrn` присутствует там, где Checko вернул данные

**Контракт шага:** `programmatic` (сборка структуры).

---

### Шаг 6 — Построить HTML-сайт

**Ожидаем:**
- Скопировать шаблон и заменить `<title>`, `CATALOG_BASE`, `EX`-массив, футер
- Запись `EX` — **bracket-match write-back** (никогда regex с `.*?`)
- Обязательные JS/CSS-фичи: `isNear`, фильтр «Почти целевые», `near-badge`, CSS-переменная
  `--nrt`, Checko-ссылка по ОГРН, `filterHint`/`updateFilterHint`

**Validation:**
- `python3 scripts/validate_site.py exhibitions/<slug>/index.html` проходит
- Массив заканчивается одним `];`, нет `]];`
- Счётчики кнопок совпадают с данными

**Контракт шага:** `programmatic` + `agent / developer / master / medium` (вёрстка/тексты `b`).

**Статус:** ✅ IMPLEMENTED (`exhibition-pipeline` Phases 5–6)

## Programmatic-шаги → `runner` (предложение)

Programmatic-шаг в контракте не называет, **чем** он исполняется (в schema v1 нет поля
`runner`/`script`). Для этого домена особенно видно разницу: часть шагов — реальные
скрипты (`scripts/validate_site.py`, `wrangler`), часть — действия (DaData/Checko/реестр).
Предлагаемое поле `runner` (schema v2) закрывает это:

| # | Шаг | Предлагаемый `runner` |
|---|-----|-----------------------|
| 2 | Спарсить список | `action: exhibition.scrape_participants` |
| 3 | Обогатить (ИНН/финансы/сайт) | `action: exhibition.enrich` (DaData + Checko) |
| **3.5** | **🔵 Проверка реестров** | **`action: registry.check` (+ `sanctions.check`)** |
| 4 | Классифицировать | `shell: scripts/classify.py` |
| 5 | Собрать `EX` | `shell: scripts/build_ex.py` |
| 6 | Построить сайт | `shell: scripts/validate_site.py` (+ agent на тексты `b`) |
| 7 | Задеплоить | `shell: npx wrangler pages deploy <slug>` |
| 8 | Git + отчёт | `action: git.open_pr` |

Как это отображалось бы в `checklist.md`:

```
- [ ] [programmatic: shell: scripts/validate_site.py] Построить сайт
- [ ] [programmatic: action: registry.check] Проверка реестров (санкции/ЕГРЮЛ)
```

## CI-сценарий (черновик): план моков

| Что мокаем | Чем | Что проверяем вместо реального |
|------------|-----|-------------------------------|
| Страницы каталога (HTTP) | сохранённые HTML-фикстуры | парсинг имени/стенда/href |
| DaData (ИНН) | фикстуры `suggest/party` | сопоставление имени → ИНН |
| Checko (финансы) | фикстуры компаний (ОКВЭД/выручка/ОГРН) | типовую и revenue-классификацию |
| 🔵 Санкционные списки | фикстуры: `ok` / `sanctioned` | что `sanctioned` не может быть `t:1` |
| 🔵 ЕГРЮЛ/ФНС | фикстуры статусов: действующая / ликвидирована / банкрот | что `inactive` не может быть `t:1` |
| `wrangler deploy` | фейковый деплой, возвращает URL | порядок «validate → deploy» |
| Внешний API LLM | не нужен (домен на скриптах/детерминированный) | — |

Детерминированные ассерты:

1. Компания без ИНН → максимум `nt:1`, никогда `t:1`.
2. 🔵 Компания из санкционного списка или с недействующим юрлицом → никогда `t:1`.
3. 🔵 Проверка реестра вызывается **до** классификации (ассерт на порядок вызовов).
4. `EX`-массив после write-back заканчивается одним `];`, без `]];`.
5. `validate_site.py` проходит до вызова `wrangler deploy`.
6. Отчёт содержит согласованные числа (компаний / ИНН / targets).

## Edge Cases в этом сценарии

| Ситуация | Ожидаемое поведение |
|----------|---------------------|
| Каталог участников недоступен | Честная ошибка, не выдуманный список |
| Компания без ИНН | Максимум `nt:1`, никогда `t:1` |
| Иностранная компания (Belarus и др.) | `not_target` (t:0, nt:0) |
| Неясный ОКВЭД/тип | `near_candidate` → максимум `nt:1` |
| Неизвестная выручка | `nt:1` (оставить, уточнить на встрече), не исключать |
| Checko недоступен / нет ОГРН | Ссылка Checko не строится; помечается «ИНН не найден»-подобно |
| 🔵 Компания в санкционном списке | Не может быть `t:1`; badge `sanctioned`; в отчёте — отдельно |
| 🔵 Юрлицо ликвидировано/банкрот | Максимум `nt:1` с предупреждением; не target |
| 🔵 Компания не найдена в реестре | `registry_status=not_found`; максимум `nt:1` |
| 🔵 Реестр недоступен (API/лимит) | Явный `unknown`, не «молча ok»; классификация не повышает до `t:1` |
| Дубликаты компаний | Дедуп по нормализованному имени |
| Сайт задеплоился с JS-ошибкой | `validate_site.py` должен поймать до отчёта |

## Проверяемые инварианты

1. **NO INN = NO t:1** — без подтверждённого ИНН и выручки в диапазоне target невозможен.
2. **🔵 Санкции/недействующее юрлицо = не target** — реестровая проверка блокирует `t:1`
   (новое требование, до классификации).
3. Пороги классификации детерминированы: unknown/`<150M` → `nt:1`, 150M–1B → `t:1`.
4. Неизвестная выручка — это `nt:1` (сохранить), а не исключение.
5. `EX`-массив записывается bracket-match, а не regex — сайт не ломается.
6. Checko-ссылка строится по **ОГРН**, не по ИНН.
7. Деплой только после прохождения `validate_site.py`; git — только через PR, не в `main`.
