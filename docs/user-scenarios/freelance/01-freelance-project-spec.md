# Freelance — Спецификация фриланс-проекта: от слов клиента до GO/NO-GO

**Домен:** Фриланс — приёмка и анализ проекта (intake & analysis)  
**Длина:** ~6 шагов  
**Репозиторий:** `trained-assist-freelance-skill` (domain skill server, sibling-репо) — **LIVE сегодня**  
**Тулы:** `freelance_new_project`, `freelance_add_info`, `freelance_assess`, `freelance_questions`, `freelance_list`, `freelance_get_project`, `freelance_generate_spec`, `freelance_get_spec`, `freelance_generation_note`, `freelance_generate_all`  
**Хранилище:** `$USERS_DIR/<profile>/Фриланс проекты/<project-slug>/`  
**Охват:** от свободного описания проекта клиентом до явного вердикта GO/NO-GO с обоснованием и рисками

> Конвейер различает **источники** (диалог/файлы/скриншоты — traceability, не текст спеки),
> **факты**, **требования**, **наши допущения** и **наше решение**. Документ описывает
> **систему**, а не разговор: никаких «клиент сказал», хронологии или ссылок на провенанс.

---

## Контекст (начальный state)

- Профиль существует; корень хранилища: `$USERS_DIR/<profile>/Фриланс проекты/`
- Проект ещё не создан (`_index.json` пуст для этого клиента)
- Клиент описывает проект freely — в диалоге, файлом или скриншотом
- Движок рисков (`lib/risk-engine.js`) детерминирован; тип проекта:
  `ai_simple | integration | ecommerce | medtech | academic | default`

## Сценарий

### Шаг 1 — Клиент описывает проект в свободных словах

```
User: клиент хочет систему, которая принимает фото товара и возвращает описание.
      есть база на Postgres, нужен веб-интерфейс, бюджет ~200к, срок — месяц.
```

**Ожидаем:**
- Бот распознаёт, что это intake нового фриланс-проекта
- Создаёт проект (`freelance_new_project`) либо находит существующий
- Пишет сырой ввод как **источник** (`provenance/log.jsonl` + при необходимости `raw/`),
  а не как спеку

**Validation:**
- Создана папка проекта со `project.json`
- Сырой ввод зафиксирован в provenance с указанием источника и надёжности
- Ничего не попало автоматически в `requirements.md` или `solution.md`

**Контракт шага (если бы это был playbook item):** `agent / researcher / bachelor / small` — intake/discovery.

**Статус:** ✅ IMPLEMENTED (`10-freelance-project.js → freelance_new_project` / `freelance_add_info`)

---

### Шаг 2 — Извлечь факты, требования и допущения (разложить по стадиям)

**Ожидаем** (каждый вызов `freelance_add_info` пишет ровно в один файл — дисциплина стадий):

- **`facts.md`** — извлечённые, дедуплицированные факты, каждый ссылается на provenance id
- **`requirements.md`** — атомарные требования о **системе**: «Система должна …»,
  без «клиент сказал»
- **`interpretation.md`** — **наши** допущения, явно помеченные как допущения
- **`solution.md`** — наше инженерное решение
- Если клиент диктует технические детали (например, «CatBoost, 127 моделей, Jupyter») —
  это **требование** (налагаемое клиентом), а не наше решение; `solution.md` вправе
  с ним согласиться или предложить иначе

**Validation:**
- `requirements.md` не содержит отсылок к диалогу/провенансу
- Допущения не просочились в требования или решение
- Открытые/неподтверждённые пункты — в короткий раздел «Открытые вопросы», не в прозу

**Контракт шага:** `agent / researcher / master / medium` (размежевание факт/требование/допущение/решение);
финальная строгая вычитка — `reviewer / master / medium`.

**Статус:** ✅ IMPLEMENTED (stage-аргумент `freelance_add_info`)

---

### Шаг 3 — Уточняющие вопросы (если неясно)

```
User: задай уточняющие вопросы по этому проекту
```

**Ожидаем:**
- `freelance_questions` формирует список неясных вопросов (по типу проекта)
- Ответы снова заводятся как intake (`freelance_add_info`), обновляя соответствующие стадии
- Диалог-логи (`qna.md`) — traceability, **не** подаётся в генерацию спеки

**Validation:**
- Вопросы релевантны типу проекта
- Ответы не «дописывают» требования задним числом — проходят обычную стадию
- `qna.md` существует, но не участвует в `_source.md`

**Контракт шага:** `agent / researcher / bachelor / small`.

**Статус:** ✅ IMPLEMENTED (`freelance_questions`)

---

### Шаг 4 — Предложить решение

**Ожидаем:**
- Из нормализованного контекста строится инженерное решение (`solution.md`)
- Решение отвечает на требования и явно учитывает допущения
- При необходимости — варианты и компромиссы

**Validation:**
- Каждое существенное требование покрыто решением или явно отложено
- Решение не выдаёт допущения за подтверждённые факты

**Контракт шага:** `agent / developer / master / medium` (архитектурное предложение);
критика — `reviewer / master / medium`.

**Статус:** ✅ IMPLEMENTED (`solution.md` через `freelance_add_info stage=solution`)

---

### Шаг 5 — Вердикт GO/NO-GO с обоснованием и рисками

```
User: дай вердикт — брать этот проект или нет
```

**Ожидаем:**
- `freelance_assess` прогоняет детерминированный risk-engine по сигналам проекта
  (предоплата, бюджет, срок, объём, тип, отношения с клиентом и т.д.)
- Результат: сигналы + score + **вердикт GO/NO-GO** + обоснование
- Для `academic`-проектов бизнес-сигналы (предоплата/бюджет/срок) не применяются —
  у задачи нет ongoing-отношений с клиентом
- Результат сохраняется в `risk-assessment.json`; таблица проектов/рисков показывается
  пользователю

**Validation:**
- `risk-assessment.json` содержит `signals`, `score`, `verdict`
- Обоснование вердикта явное, риски перечислены
- Вердикт детерминирован — повторный `freelance_assess` на тех же данных даёт тот же вердикт

**Контракт шага:** `programmatic` (детерминированный движок) + `agent / reviewer / doctor / medium`
для человекочитаемого обоснования вердикта.

**Статус:** ✅ IMPLEMENTED (`lib/risk-engine.js`, `freelance_assess`)

---

### Шаг 6 — Сгенерировать спеку (long/short)

**Ожидаем:**
- Нормализованный контекст `spec/_source.md` — единственный вход для обоих вариантов
- `spec/long.md` — подробная спека для исполнителя
- `spec/short.md` — независимая executive-спека для клиента (**не** сокращение `long`)
- Постоянные правила генерации: `_generation.md` (профиль) и `<project>/generation.md`
  (проект, приоритетнее) применяются к каждой последующей генерации
- Точечная правка (`«убери раздел X»`) редактирует существующий файл in place, и
  инструкция пользователя важнее шаблона

**Validation:**
- `_source.md` не содержит «клиент сказал», хронологии, meta-разделов о допущениях
- `long` и `short` сгенерированы независимо из одного `_source.md`
- `freelance_generate_spec variants=long|short|both` работает по разу

**Контракт шага:** `agent / developer / master / large` (генерация документа);
проверка — `reviewer / doctor / medium`.

**Статус:** ✅ IMPLEMENTED (`freelance_generate_spec`, `freelance_get_spec`)

## Programmatic-шаги → `runner` (предложение)

У фриланса «скрипты» — это не shell-команды, а **MCP-тулы** скилла. Поэтому поле
`runner` (schema v2) должно уметь ссылаться на действие, а не только на файл:

| # | Шаг | Предлагаемый `runner` |
|---|-----|-----------------------|
| 1 | Intake (сырой ввод → provenance) | `action: freelance.add_info (stage=provenance)` |
| 2 | Факты / требования / допущения | `action: freelance.add_info (stage=facts \| requirements \| interpretation)` |
| 4 | Предложить решение | `action: freelance.add_info (stage=solution)` |
| 5 | GO/NO-GO вердикт | `action: freelance.assess` (`lib/risk-engine.js`) + agent на обоснование |
| 6 | Генерация спеки long/short | `action: freelance.generate_spec (variants=long \| short \| both)` |

Как это отображалось бы в `checklist.md`:

```
- [ ] [programmatic: action: freelance.assess] GO/NO-GO вердикт
- [ ] [programmatic: action: freelance.generate_spec] Генерация спеки long/short
```

## CI-сценарий (черновик): план моков

| Что мокаем | Чем | Что проверяем вместо реального |
|------------|-----|-------------------------------|
| LLM/OpenRouter (агентные шаги, генерация спеки) | скриптованные ответы/фикстуры `long.md`/`short.md` | стадийность и отсутствие утечек диалога |
| risk-engine | **не мокаем** — он детерминированный и офлайн (`lib/risk-engine.js`) | вердикт на фиксированных сигналах |
| Файловое хранилище `Фриланс проекты/` | временный `USERS_DIR` | раскладку файлов и изоляцию по профилю |
| Классификатор документа | фикстуры ответов дешёвой модели | маршрутизацию по содержанию, а не по имени |

Детерминированные ассерты:

1. Сырой ввод попадает только в `provenance/log.jsonl`, **не** в `requirements.md`/`solution.md`.
2. Стадии не смешиваются: один `add_info` пишет ровно один файл.
3. Одни и те же сигналы → один и тот же вердикт (детерминизм risk-engine).
4. `academic`-проект: бизнес-сигналы не влияют на вердикт.
5. `long` и `short` сгенерированы независимо из одного `_source.md`.
6. Классификатор документа не спавнит Claude-сессию (только cheap-LLM).

## Классы риска (тип проекта → сигналы)

| Тип | Особенность оценки |
|-----|--------------------|
| `ai_simple` | Сигналы, связанные с данными и неопределённостью моделей |
| `integration` | Зависимость от внешних API/систем |
| `ecommerce` | Платёжные/каталожные риски |
| `medtech` | Регуляторика/чувствительность данных |
| `academic` | Бизнес-сигналы (предоплата, бюджет, срок) **не применяются** — нет ongoing-клиента |
| `default` | Базовый набор из 8 бизнес-сигналов |

## Edge Cases в этом сценарии

| Ситуация | Ожидаемое поведение |
|----------|---------------------|
| Клиент даёт только PDF-задачу без имени/цены/срока | Тип `academic`; бизнес-сигналы не применяются |
| Клиент не дал бюджет/срок | Сигнал «неизвестно», вердикт с явной пометкой риска |
| Клиент сам диктует стек | Это **требование**, не наше решение; решение вправе оспорить |
| Противоречия между источниками | Новый факт помечает противоречие (`contradicts` в provenance) |
| Генерацию просят без достаточных данных | Сначала уточняющие вопросы, затем спека |
| Повторная генерация | Правила `generation.md` применяются; правки in place не восстанавливают удалённый раздел |
| Два похожих проекта у одного профиля | `freelance_classify_document` маршрутизирует документ по содержанию (не по имени), recency — только prior |
| API OpenRouter недоступен | Понятная ошибка; классификатор документа не спавнит Claude-сессию |

## Проверяемые инварианты

1. **Источники ≠ спека.** Сырой ввод/диалог никогда не попадают в итоговый документ
   автоматически; они — только traceability.
2. **Стадии не смешиваются.** Один вызов `freelance_add_info` пишет ровно в один файл;
   «клиент сказал» не может просочиться в требования, а наша архитектура — в требования.
3. **Вердикт GO/NO-GO детерминирован** (risk-engine), с явным обоснованием и рисками.
4. **`academic` не оценивается бизнес-сигналами** — у задачи нет ongoing-отношений.
5. **`long` и `short` генерируются независимо** из одного `_source.md`; `short` — не
   сокращение `long`.
6. **Хранилище — profile root**, а не `process.cwd()`: проект виден из любого топика
   одного профиля.
7. **Классификатор документа — только cheap-LLM (OpenRouter)**, никогда не спавнит
   Claude Code.
