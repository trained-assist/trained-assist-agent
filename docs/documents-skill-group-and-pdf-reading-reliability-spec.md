## 1. Как хорошо `pdftotext` читает PDF — замер

Проверка на 12 реальных PDF из `~/Downloads` (резюме, презентации, справки, сканы-подобные макеты), `pdftotext -layout` (poppler 25.09):

| Что | Результат |
|-----|-----------|
| Текстовые PDF (резюме, письма, справки, Сколково) | Читаются полностью, кириллица без искажений |
| «Битые символы» у LEYA_Academy_Concept (156 шт.) | Не потеря текста — это значки-буллеты из шрифта-иконок (private-use glyphs). Безвредно, можно вычищать regex-ом |
| Дизайнерские макеты (`Премиум уход для ног` — 171 симв./стр., `presentation_final` — 561 симв./стр. при 31 картинке, `Инструкция по интеграции` — 454 симв./стр. при 4 картинках) | **Читается только часть**: текст, запечённый в картинки, теряется молча — без ошибки |
| Полностью отсканированные PDF (одни картинки) | В выборке не было. Но известное поведение: `pdftotext` возвращает **пустую строку с exit 0** — не ошибку |

**Вывод:** «всегда хорошо» — нет. На цифровых PDF надёжен и бесплатен. Опасность в **тихих отказах**: пустой или частичный результат выглядит как успех. Поэтому нужен не «ретрай того же», а **лестница с проверкой качества между ступенями**.

OCR как запасной вариант тоже не панацея: `tesseract rus+eng` (150 dpi) на стилизованном слайде `presentation_final` (стр. 3) вернул 0 символов, хотя `pdftotext` там нашёл 611. На плотном декоративном дизайне OCR слабее. Для таких страниц последняя ступень — vision-LLM. (Это один замер на одной странице, не статистика.)

### Предлагаемая лестница (`doc_read`)

1. `pdftotext -layout` (бесплатно, миллисекунды).
2. **Проверка качества** на каждую страницу: `chars/стр < ~200` или (`картинок на стр. ≥ 1` и `chars/стр < ~600`) → страница помечается «подозрительной». Вычистить PUA-символы (`–`) перед подсчётом.
3. Подозрительные страницы → `pdftoppm -r 200` + `tesseract -l rus+eng`. Брать результат OCR, только если он дал **больше** символов, чем шаг 1 (склеивать, не заменять).
4. Если и после OCR страница пустая/скудная → render в PNG + дешёвая vision-модель через OpenRouter (Gemini 2.5 Flash — по правилу репо «recruiter/quick tools не зовут Claude Code»). Только для этих страниц, не для всего файла.
5. Ответ **всегда несёт метаданные**: `method` по каждой странице (`text` / `ocr` / `vision`), `low_confidence_pages: [..]`. Агент честно говорит пользователю «стр. 3, 7 распознаны OCR, могут быть неточности» вместо молчаливого успеха.

Ретрай ≠ повтор того же вызова: `pdftotext` детерминирован, повтор ничего не даст. Ретрай имеет смысл только для сетевых ступеней (vision-LLM, Cloudflare) — с таймаутом (`AbortSignal.timeout`) и одной повторной попыткой.

### Cloudflare AI (`toMarkdown`)

Пользователь спросил про «Cloudflare AI function». У Workers AI есть конвертация документов в Markdown (PDF, изображения, docx, xlsx, html). **Я это не проверял** — в этой сессии нет доступа/измерений. Что нужно проверить перед решением: (а) качество на тех же 12 файлах (особенно дизайнерские макеты и кириллица), (б) цена/лимиты, (в) отправка файла наружу — есть ли среди PDF конфиденциальные (резюме кандидатов, документы клиентов). Пока — кандидат на ступень между 3 и 4, не замена `pdftotext`.

### Что проверить на VM (не проверено)

`pdftotext`/`pdftoppm`/`tesseract` есть на Mac. На GCP VM tesseract стоит (см. память проекта), но наличие `poppler-utils` и языкового пакета `rus` для tesseract на **обеих** VM (GCP и RU) — не подтверждено. Без этого лестница молча деградирует. Скил должен на старте проверять бинарники и возвращать `isReady()=false` / понятную ошибку.

## 2. Где живёт работа с документами — структура скилов

**Решение (рекомендация):** одна тематическая группа «Документы» в соседних номерах рядом с `50-gdrive.js` (диапазон `51–59` свободен; проверено `ls tools/`), а не россыпь по одному файлу на формат в случайных местах.

| NN | Файл | Что делает |
|----|------|-----------|
| 51 | `51-doc-read.js` | `doc_read` — чтение PDF/docx/xlsx/html/txt в текст/markdown; лестница из §1; возвращает метаданные качества |
| 52 | `52-doc-generate.js` | `doc_generate` — HTML → PDF (headless Chrome/Playwright, уже стоит на VM), markdown/HTML → docx, таблицы → xlsx. Вход: HTML/markdown + шаблон |
| 53 | `53-doc-templates.js` | шаблоны/брендинг отчётов (HR Stalker, Flexi, …) — общий каркас для печатных отчётов; сюда же уходит #376-подобное (candidate report) |
| 54 | (резерв) | `doc_convert` / слияние, разбивка PDF, если понадобится |

Границы с существующим:
- `94-tg-send.js` — доставка файла пользователю; `doc_generate` возвращает путь, отправку делает `tg_send_file`.
- `97-publish.js` / `84-artifacts.js` — публикация страницы по ссылке; печатный PDF-отчёт — другой сценарий (файл), но HTML-шаблон можно переиспользовать для обоих.
- `50-gdrive.js` — Google Docs (облачные); `doc_read` читает **локальные файлы**, для Google Docs остаётся gdrive.
- Модули с ядром чтения (лестница) выносить в `src/documents/` (обычный модуль, не MCP), а скил — тонкая обёртка: логику можно тестировать без MCP и вызывать из `runner.js` quick answer'ов.

Правила, которые тянет за собой группа:
- Чтение/OCR/vision — **без Claude Code** (дешёвые модели через OpenRouter, локальные утилиты). Иначе теряется смысл «бесплатного» пути.
- Внешние вызовы — с таймаутом; временные файлы — в рабочую директорию профиля (`AGENT_DATA_DIR/sessions/<username>/`), не в `/tmp`.
- Утилиты (`pdftotext`, `tesseract`) вызывать через `execFile` с массивом аргументов, не через shell — имена файлов приходят от пользователя.
- Новый скил → обновить таблицу занятых номеров в `docs/how-to-add-skill.md` и `00-meta.js` каталог.

1. `src/documents/pdf-read.js` — лестница §1 + quality-check + юнит-тесты на фикстурах: текстовый PDF, скан, макет с картинками, PDF с PUA-буллетами.
