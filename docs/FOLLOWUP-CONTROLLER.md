# Followup Controller (GTD-модуль)

Не «персистентный контроль деплоя», а **извлечение намерения довести задачу до конца**.
Класс проблемы: юзер просит проконтролировать, что задача реально доделана, а не потерялась
после первой итерации. Решаем в коде скила (общий для всех), проверяемо запуском.

## Поток
1. **Intent-gate (дешёвая LLM).** На запросе юзера дешёвая модель классифицирует:
   просит ли юзер проконтролировать доведение до конца? → `followup: {wanted, etaMinutes}`.
   Консервативно: сомнение → `wanted:false` (ложный пинг дороже пропуска).
2. **Постановка таймера.** При запуске первого Claude, если `wanted` — пишем durable-запись
   `followups/<sessionId>.json` = `{sessionId, dueAt, iterations:0, maxIterations, status}`.
   ETA по умолчанию 60 мин (позже — оценка по типу задачи).
3. **Срабатывание (tick сервера).** Когда `now >= dueAt` И **сессия idle/finished**
   (re-entrancy guard) — переоткрываем ту же сессию сообщением:
   > Проверь: всё ли по задаче сделано? Если да — подтверди и заверши.
   > Если нет — сделай ещё итерацию. ПЕРЕД итерацией: создай issue на то, что собираешься
   > делать, потом выполни. Если есть старые открытые issue с прошлого шага — бери их в работу
   > и двигай дальше.
4. **Терминал.** Итерация отчиталась «done» ИЛИ нет прогресса по open-issue ИЛИ
   `iterations >= maxIterations` → `status:closed`, таймер снят.

## Обязательные гарды (иначе не мержим)
- **Re-entrancy:** не переоткрывать сессию, если первый Claude ещё жив
  (уже ловили дубль-claude на общем agent-data). Проверять состояние в session-store.
- **Hard cap:** `maxIterations` (дефолт 3). Самопинг без потолка = бесконечный костью и деньги.
- **Durable:** запись на диске, переживает краш; отчёт по факту с диска, не по памяти.
- **Issue-ledger:** каждый шаг = GitHub issue (см. [[issues-as-durable-record]]) —
  аудируемо, и цикл поднимает недоделанные issue вместо потери контекста в сессии.

## Дефолты v1
`etaMinutes=60`, `maxIterations=3`, intent-gate на дешёвой модели, issue-first протокол.
